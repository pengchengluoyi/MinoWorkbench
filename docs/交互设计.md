# 交互设计 · 主路径三个页面

> 方法：用户目标 → 信息架构 → 界面表现 → 交互行为 → 系统状态 → 质量保障。
> UI 解决"看得懂、看得舒服、一致"，交互解决"找得到、做得顺、错能恢复"。

## 0. 先承认一件事

此前几版的信息架构是**原数据模型的镜像**，不是设计结果。

「用例 / 任务 / 导航 / 测试资源 / 配置」这五项按**后端资源**切分，而用户脑子里是一条连续动线：

```
挑一批用例  →  下发  →  哪条挂了  →  为什么挂
```

这条动线被切成两个互不相干的目的地：在用例页选完，要自己走到任务页去找刚下发的批次。**这是搬，不是设计。**
落地页同理——按项目分 section 是 `project.apps` 的结构，不是使用方式；大多数项目只有一个应用，分组这层纯属开销。

下面三页按动线重做。

---

## 一、落地页 `/testing`

### 用户目标

| 频次 | 目标 |
|---|---|
| 每天多次 | **进到我要测的那个应用**。纯导航，越快越好 |
| 每天一次 | 看一眼有没有东西在跑 |
| 低频 | 建项目 / 建应用 |

### 信息架构

- 原设计按项目分 section：一个项目一个标题 + 一个网格。**大多数项目只有 1 个应用**，等于给一个卡片配一套分组装饰。
- 改为**单一列表，一行一个应用**；项目名降级为行内副信息。
- 排序按"下一步最可能点谁"：**执行中 → 最近打开过 → 名称**。
- 按项目分组保留为可选开关（项目多时才有价值），默认关。

### 界面表现

- 一行：图标 · 应用名 + 项目名 · 覆盖端 · 执行中 · `→`
- 行高跟随密度 token（舒适 44 / 紧凑 32）。**一屏可见 10+ 个应用**，原网格方案只有 4 个。
- 概览数字压成一条细横条，不再是三个占高度的卡片。

### 交互行为

- 搜索即时过滤并显示匹配数。
- **键盘可完成全流程**：`/` 聚焦搜索，`↑↓` 移动，`Enter` 进入。高频导航页不该强制用鼠标。
- 最近打开过的置顶并标注。
- 整行可点，不是只有标题可点。

### 系统状态

加载骨架行 · 无项目（引导建项目）· 项目下无应用 · 搜索无结果 · 列表读取失败（可重试）· **计数接口降级时列表照常可用**

### 质量保障

- [ ] 一屏（1080p）可见应用 ≥ 10 个
- [ ] 不用鼠标能完成"搜索 → 进入应用"
- [ ] 计数接口 500 时列表仍然可用

## 二、用例 `?tab=cases`

### 用户目标

| 频次 | 目标 |
|---|---|
| 核心 | **挑一批用例跑起来** —— 整个产品的主动作 |
| 高 | 这条用例是什么 / 上次为什么挂 |
| 低 | 导入、改、删用例 |

### 信息架构

- 原设计把"选用例"和"下发"切成两步两处：选完要去别处找入口。
- 改为**选择即准备下发**：多选 → 底部浮动操作条常驻「跑选中的 N 条」。**主动作永远在视野里。**
- **模块树降级为筛选器**（左侧可折叠），不再当导航层级用。
- **上次执行结果是用例行的一等信息**。选哪些用例跑，真实依据就是"哪些一直在挂"，不该要点进去才看到。

### 界面表现

- 左：模块筛选，可折叠
- 右上：搜索 + 结果筛选（全部 / 上次失败 / 从未跑过）
- 右：用例表，紧凑，**失败行左侧红条**
- 底：选中后浮出操作条（选中数 · 设备 · 跑）

### 交互行为

- **下发后不跳页**：就地出现执行条（进度 + 查看详情）。用户不丢上下文——这是对原设计最重要的一处修正。
- 行内展开看步骤，不跳页。
- 失败行**直接显示上次失败原因摘要**。
- **下发前置校验前移**：没选用例 / 没有在线设备 → 按钮禁用并写明原因，而不是点了才报错。

### 系统状态

无用例（引导导入）· 加载 · 下发中 · 下发失败（**不清空已选**）· **无在线设备**（最常见的前置失败，必须前置提示）

### 质量保障

- [ ] 选中 → 下发全程不换页
- [ ] 无在线设备时按钮禁用且说明原因
- [ ] 下发失败后已选用例不丢

## 三、任务 `?tab=tasks`

### 用户目标

| 频次 | 目标 |
|---|---|
| 核心 | 刚跑的那批怎么样了（监控） |
| 核心 | **为什么挂了**（诊断）—— 真正花时间的地方 |
| 中 | 这条用例是不是一直在挂（趋势） |

### 信息架构

- 原设计是时间倒序的任务列表 + 详情面板。**列表是陈列，不是答案**：用户要的是"最近这批的结果"，却每次都得先在列表里找。
- 改为**默认落在最近一个批次的结果**。批次选择器收成顶部一个控件。
- 批次内**按需要关注排序**：失败 → 异常 → 跳过 → 通过。100 条通过是噪音。
- 三层下钻**都在同一页内**：批次 → 失败用例 → 失败步骤，不跳页。

### 界面表现

- 顶：批次选择器（最近若干个，带状态点）+ 概览（进度 / 通过 / 失败）
- 主：用例结果表，**失败置顶**，带失败原因摘要
- 右：选中用例的步骤时间线（分栏，不是弹窗——诊断时要同时看列表和步骤）

### 交互行为

- 执行中实时追加结果；**用户手动滚动后停止自动跟随**（原实现无条件滚到底，正在看前面的步骤会被拽走）。
- 「只看失败」一键切换，且**默认就只看需要关注的**。
- 失败用例可直接重跑这一条。
- **实时断线显式提示** + 手动刷新，不静默停更。

### 系统状态

从没跑过 · 执行中 · 已完成 · 批次不存在 · **实时断线** · 截图缺失（占位，不破图）

### 质量保障

- [ ] 进页 3 秒内看到最近一个批次的结果
- [ ] 失败用例在首屏可见，不需要滚动或筛选
- [ ] 实时断线有提示，且能手动恢复

## 四、贯穿三页的几条规则

| 规则 | 为什么 |
|---|---|
| 主动作常驻视野 | 用例页的「跑」、任务页的「重跑」不该藏在二级入口 |
| 下发 / 跳转后不丢上下文 | 丢上下文是用户最常抱怨的"难用" |
| 前置条件不满足就禁用并说明 | 让人点一下再报错，是把校验成本转给用户 |
| 默认只看需要关注的 | 通过的用例是噪音，失败才需要人 |
| 列表优先于网格 | 本产品的数据密度高，网格浪费垂直空间 |
| 状态语义给三件：颜色 + 图标 + 文字 | 只靠颜色，色觉障碍用户读不出来 |
